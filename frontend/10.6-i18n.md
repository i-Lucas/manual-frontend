# 10.6 Feature Global — Internacionalização (i18n)

A aplicação roda em **múltiplos idiomas** (hoje `pt` e `en`). Trocar de idioma é apenas **carregar outro conjunto de textos** — nenhum texto de UI fica escrito no meio do código. Todo texto visível ao usuário vem de um arquivo de idioma dedicado por módulo.

> **Regra de ouro:** se uma string aparece na tela, ela vive num arquivo de idioma — nunca no `.tsx`, no hook ou no service. String literal de UI no meio do código é um erro de arquitetura, igual a um `style={{}}` inline.

## Por que é uma feature global

O idioma é transversal a toda a aplicação: muda uma vez e a interface inteira reflete. Centralizar o estado do idioma, a resolução de chaves e a reatividade num único lugar evita que cada módulo reinvente o mecanismo — exatamente como cache, HTTP e EventBus. Os módulos só contribuem com seus **arquivos de texto**; o motor é global.

## Os dois lados

| Lado | Onde | Responsabilidade |
|---|---|---|
| **Motor global** | `src/services/i18n/` + `src/context/I18nContext.tsx` + `src/hooks/useT.ts` | Estado do locale, persistência, registro de dicionários, resolução de chave, reatividade |
| **Textos do módulo** | `src/modules/Module/i18n/module.{pt,en}.json` | Apenas o conteúdo traduzido, organizado por componente |

## Formato dos arquivos de texto (JSON, um por idioma)

Cada módulo tem **um arquivo JSON por idioma**, nomeado `{namespace}.{locale}.json`. O `namespace` é o nome do módulo (em minúsculas) e vira a raiz da chave. Dentro de cada arquivo, **as chaves de primeiro nível são os componentes** do módulo; abaixo delas, as strings.

```jsonc
// src/modules/Approvals/i18n/approvals.pt.json
{
  "header":  { "title": "Casos do Sistema", "subtitle": "Solicitações aguardando revisão do gestor" },
  "filters": { "all": "Todos" },
  "card":    { "history": "Histórico", "notePlaceholder": "Nota ou motivo..." },
  "actions": { "approve": "Aprovar", "reject": "Rejeitar", "cancel": "Cancelar" },
  "status":  { "PENDING": "Pendente", "APPROVED": "Aprovado", "REJECTED": "Rejeitado" }
}
```

```jsonc
// src/modules/Approvals/i18n/approvals.en.json — MESMAS chaves, outro idioma
{
  "header":  { "title": "System Cases", "subtitle": "Requests awaiting manager review" },
  "filters": { "all": "All" },
  "card":    { "history": "History", "notePlaceholder": "Note or reason..." },
  "actions": { "approve": "Approve", "reject": "Reject", "cancel": "Cancel" },
  "status":  { "PENDING": "Pending", "APPROVED": "Approved", "REJECTED": "Rejected" }
}
```

> **Regra:** o arquivo `.en.json` deve ter **exatamente as mesmas chaves** do `.pt.json`. Adicionar um texto = adicionar a chave nos dois arquivos. Uma chave que existe só em um idioma é um bug — a UI mostrará a própria chave no idioma faltante.

### Registro automático por convenção de path

Nenhum código de registro manual. O motor descobre todos os dicionários via `import.meta.glob('/src/modules/**/i18n/*.json')` — basta criar o arquivo seguindo o padrão `{namespace}.{locale}.json` e ele entra no registro sob aquele `namespace`. Textos verdadeiramente globais (compartilhados por vários módulos) vão em `src/i18n/common.{locale}.json` → namespace `common`.

### Carregamento sob demanda (13-08-2026)

O glob **não** é `eager`: cada dicionário é um chunk próprio. Carrega-se o idioma **ativo** — mais o **padrão** junto, quando o ativo é outro, porque `scope()` recorre a ele quando falta uma chave. Quem espera é o **boot** (`i18nService.loadInitial()`, com await antes do primeiro render) e o **loader da rota**; por isso **`useT` continua síncrono** e nenhum componente precisa saber que houve download.

Antes, todo namespace de todo idioma entrava no bundle inicial: 978 KB de JSON, dos quais 657 KB eram os nove guias — baixados inclusive pelo cliente de produção, que os vê como "Em breve".

**Namespaces adiados (`DEFERRED_NAMESPACES`).** Namespace de texto grande que a maioria das sessões nunca lê fica fora da carga inicial e é pedido pela rota que o usa:

```ts
// router/routes.ts — o dicionário vem em paralelo com o chunk da página
export const StockGuidePage = lazyRoute(
  () => import('../modules/Guides/StockGuide/StockGuide'),
  { namespace: 'guides' },
)
```

> ⚠️ **Rota que apenas MEDE o texto também precisa declarar o namespace.** Os cards da Central de Ajuda contam seções e tempo de leitura dos nove guias (`useGuideMetrics` → `i18nService.getMessages`), então `/support` declara `guides` mesmo sem exibir guia nenhum. Sem isso o dicionário vem vazio e a métrica some **em silêncio** — nenhum erro, só um número que não aparece.

Quando adiar: o namespace é grande **e** concentrado numa rota. Namespace de módulo comum (`stock`, `scheduling`) fica na carga inicial — ele é pequeno e o shell precisa dele.

## Como os componentes consomem: hook `useT`

Qualquer componente — **incluindo o Presenter** — chama o hook global `useT(scope)`, onde `scope` é `namespace` + caminho opcional até o grupo desejado. O retorno é uma função tradutora `t`:

```tsx
import { useT } from '@/hooks/useT'

function ApprovalCardActions() {
  const t = useT('approvals.actions')
  return (
    <div className="d-flex gap-2">
      <button className="btn btn-success">{t('approve')}</button>
      <button className="btn btn-danger">{t('reject')}</button>
      <button className="btn btn-outline-secondary">{t('cancel')}</button>
    </div>
  )
}
```

### Interpolação e pluralização

```tsx
const t = useT('approvals.pagination')

t('pageInfo', { page: 2, totalPages: 5 })  // "página 2 de 5"   (template: "página {page} de {totalPages}")
t.plural('case', total)                     // "1 caso" / "7 casos"
//   lê as chaves "case_one" e "case_other"; injeta {count} automaticamente
```

Templates usam `{nome}` para variáveis. `t.plural(key, count)` escolhe `key_one` (count === 1) ou `key_other` (qualquer outro), e disponibiliza `{count}`.

### Reatividade

`useT` lê o locale atual via Context. Quando o usuário troca de idioma, o Context atualiza e **todo componente que usa `useT` re-renderiza** — inclusive os memoizados, porque consumir Context fura o `memo`. Não é preciso passar idioma por props nem remontar nada.

## Exceção ratificada à pureza dos componentes

O manual proíbe Presenters de consumir hooks (`07-componentes.md`, `13-checklist.md`). **`useT` é a única exceção.** A justificativa: texto é **conteúdo**, não lógica nem dado de negócio — consumir `useT` é da mesma natureza que importar a util global `formatDate` ou um mapa de constantes, coisas que os Presenters já fazem. Toda outra regra de pureza permanece: Presenter continua proibido de consumir hooks de estado/dados, services ou factories. **`useT` entra; o resto continua de fora.**

## Glossário: os termos do produto (`common.terms`)

Alguns substantivos do domínio aparecem em **dezenas de frases espalhadas por vários
módulos** — e são justamente os que o cliente pede para renomear ("anomalia" ficou
estranho; passou a ser "ocorrência"). Trocar o termo caçando string por string em seis
arquivos de idioma é o mesmo problema que as constantes resolvem para números mágicos.

O motor injeta o bloco `terms` do `common.{locale}.json` como **variáveis de
interpolação em toda tradução**. A frase escreve o placeholder; o termo vive num lugar só:

```jsonc
// src/i18n/common.pt.json — a ÚNICA definição do termo
{ "terms": { "occurrence": "ocorrência", "occurrences": "ocorrências",
             "Occurrence": "Ocorrência", "Occurrences": "Ocorrências" } }
```

```jsonc
// qualquer módulo — nenhum ponto de uso sabe qual é a palavra
"title":     "⚠️ Relatar {Occurrence}",
"typeLabel": "Tipo de {occurrence}",
"empty":     "Nenhuma {occurrence} registrada"
```

Regras:

- **Uma entrada por FORMA usada** (minúscula/maiúscula, singular/plural) — a interpolação
  é substituição de texto, não gramática. A chave maiúscula começa com maiúscula
  (`{Occurrence}`), a minúscula não.
- Termo de glossário é para o substantivo que se **repete entre módulos** e pode ser
  renomeado pelo cliente. Texto que existe num módulo só continua sendo texto do módulo.
- Variável explícita do chamador **vence** o glossário (mesmo nome = intenção local).
- Frase que fica torta com o termo novo se **reescreve** (é português, não template): o
  glossário troca a palavra, não conserta a concordância em volta dela.

## Estrutura do motor global

```
src/models/
└── i18n.types.ts            ← Locale, Messages, Translator (tipos globais)
src/services/i18n/
├── i18n.constants.ts        ← LOCALES, DEFAULT_LOCALE, LOCALE_STORAGE_KEY, LOCALE_LABELS,
│                              DEFERRED_NAMESPACES, GLOSSARY_*
├── localeStore.ts           ← locale atual + persistência (localStorage)
├── i18nRegistry.ts          ← import.meta.glob (sob demanda) → { namespace: { pt, en } };
│                              loadLocale / ensureNamespace; escopo + glossário
├── translate.ts             ← funções puras: resolve chave + interpola + pluraliza
└── i18nService.ts           ← facade: getLocale / setLocale / createTranslator
                               / loadInitial / ensureNamespace / getMessages
src/contexts/
└── I18nContext.tsx          ← I18nProvider + useLocale (estado reativo do idioma)
src/hooks/
└── useT.ts                  ← hook global: useT(scope) → Translator
```

### Tipos globais

```ts
// src/models/i18n.types.ts
export type Locale = 'pt' | 'en'
export type Messages = { [key: string]: string | Messages }
export interface TVars { [k: string]: string | number }
export interface Translator {
  (key: string, vars?: TVars): string
  plural: (key: string, count: number, vars?: TVars) => string
}
```

### Estado e troca de idioma

`localeStore` guarda o locale (com persistência em `localStorage`). `i18nService.setLocale()` grava e **emite `i18n:locale:changed` no EventBus**; o `I18nProvider` ouve esse evento e atualiza o estado React → re-render global. Assim, qualquer código (até fora do React) pode trocar o idioma chamando `i18nService.setLocale()`, e a UI reage.

`setLocale` é **assíncrono**: carrega os dicionários do idioma novo (incluindo os namespaces adiados que já foram pedidos na sessão — trocar de idioma dentro de um guia precisa trazer o guia no idioma novo) e só então grava e emite. A tela nunca chega a renderizar com dicionário vazio. Se a carga falhar, a promessa rejeita e o idioma **permanece o atual** — melhor que uma tela de chaves cruas.

```ts
// Registrar o evento em eventBus.types.ts (obrigatório antes de usar)
'i18n:locale:changed': { locale: Locale }
```

O `I18nProvider` é montado no topo da árvore de providers (idioma muda raramente → fica por fora), em `AppProvider`. Um seletor de idioma (no shell/`AppLayout`) chama `useLocale().setLocale(...)`.

## Pontes para módulos ainda não migrados

Um módulo legado (ainda PT-only) que consome labels de um módulo já migrado **não** deve quebrar. O padrão: o módulo migrado mantém a **fonte única no `.pt.json`** e expõe um mapa PT derivado dele no seu `constants/`, para o consumidor legado importar via shim.

```ts
// constants/approvals.constants.ts — mapa legado derivado do .pt.json (fonte única)
import approvalsPt from '../i18n/approvals.pt.json'
import type { ApprovalRequestStatus } from '../models/approvals.types'

/** Mapa PT para consumidores legados (Stock não-migrado). Fonte: approvals.pt.json. */
export const APPROVAL_STATUS_LABELS: Record<ApprovalRequestStatus, string> = approvalsPt.status
```

O consumidor legado segue em PT (correto — ele ainda não é bilíngue); quando migrar, troca o import pelo `useT`. Sem duplicação de texto: o PT vive só no JSON.

## Adicionar um novo idioma

1. Criar `module.{novoLocale}.json` em **cada** módulo (mesmas chaves do `.pt.json`) + `src/i18n/common.{novoLocale}.json`.
2. Adicionar o código em `LOCALES` e o rótulo em `LOCALE_LABELS` (`i18n.constants.ts`).
3. Estender o union `Locale` em `src/models/i18n.types.ts`.

Nenhuma mudança em componentes, hooks ou services.

## Checklist de i18n

- [ ] Nenhuma string de UI literal em `.tsx`, hook ou service — tudo via `useT`
- [ ] Cada módulo tem `i18n/module.pt.json` e `i18n/module.en.json` com **as mesmas chaves**
- [ ] Chaves organizadas por componente (1º nível = componente)
- [ ] `useT` é o único hook consumido por Presenters — nenhum outro
- [ ] Interpolação via `{var}`; pluralização via `key_one`/`key_other` + `t.plural`
- [ ] Mapas de label legados (para módulos não-migrados) derivados do `.pt.json`, sem duplicar texto
- [ ] Termo do domínio repetido entre módulos vem do glossário (`common.terms`), não escrito na frase
- [ ] Novo idioma = novos arquivos + `LOCALES`/`LOCALE_LABELS`/`Locale`, sem tocar componentes
- [ ] Rota que usa (ou apenas MEDE) um namespace de `DEFERRED_NAMESPACES` o declara no `lazyRoute`
