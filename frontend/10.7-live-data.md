# 10.7 Feature Global — Camada LIVE (recursos de dados vivos)

**Esta camada é o motor que materializa a Filosofia (§0) em código único.** Os três princípios — cache-first, "o cliente sabe o que mudou" e granularidade máxima — deixam de ser um padrão que cada módulo religa à mão (chave de cache + TTL + fetch + evento de EventBus + listener no hook) e passam a ser **uma declaração por recurso**. Implementada uma vez em `src/services/live/`, consumida por todos os módulos.

## Por que existe

Antes da camada LIVE, cada fluxo de dado reativo exigia ligar manualmente ~8 pontos: a chave de cache, o TTL, o fetch cache-first no service, um evento próprio no `eventBus.types`, o emit na invalidação, o listener no hook, o estado de loading e o re-fetch silencioso. O mesmo hook foi escrito quatro vezes (históricos de Cargos, Procedimentos, Estoque-módulo e Estoque-produto) — e cada ponto esquecido virava um bug de reatividade (dado que não aparecia sem F5, aba que não atualizava). A camada LIVE elimina a religação: **o que é igual em todos os fluxos vive no motor; o módulo declara só o que é dele** (chave, TTL, fetch).

## O conceito: recurso vivo

Um **recurso vivo** (`defineLiveResource`) é um canal de dado declarado uma única vez no service-facade do módulo:

```ts
// no service-facade do módulo (ex.: rolesService.ts)
export const roleHistoryLive = defineLiveResource<RoleHistoryEntry[], []>({
  key: () => 'roles:history',        // chave canônica no cacheService (§10.1)
  ttl: CACHE_TTL.DEFAULT,
  fetch: async () => { /* via getStrategy() — demo/real decidido aqui */ },
})

// família com argumentos (uma instância por produto):
export const productEditHistoryLive = defineLiveResource<ProductHistoryEntry[], [productId: string]>({
  key: id => `stock:manage:edit-history:${id}`,
  prefix: 'stock:manage:edit-history:',   // habilita invalidateAll()
  ttl: CACHE_TTL.DEFAULT,
  fetch: async id => { /* ... */ },
})
```

Sobre o recurso, as operações cobrem os três caminhos de mudança de dado:

| Operação | Quando usar | Efeito nos consumidores |
|---|---|---|
| `of(...args).set(data)` | **O autor da mutação tem o dado** (resposta da API) ou o broadcast carregou a entidade | UI atualiza NA HORA, **zero fetch** (§0.2) |
| `of(...args).patch(fn)` | Atualização cirúrgica de parte do dado cacheado | Idem — só o que mudou re-renderiza |
| `of(...args).invalidate()` | O dado novo **nasceu no servidor** (ex.: entrada de audit) ou o sinal cross-client veio sem a entidade | Consumidores montados re-buscam em **SILÊNCIO** (sem skeleton) |
| `of(...args).get()` | Leitura cache-first programática (com dedup de requests em voo) | — |
| `invalidateAll()` | Invalidação ampla de uma família (exige `prefix`) | Idem invalidate, para todas as instâncias |

## O hook: `useLive`

Todo componente consome recursos vivos pelo MESMO hook — nenhum módulo reimplementa cache-first/listener/loading:

```ts
const { data, loading } = useLive(roleHistoryLive, [], { enabled: show })
const edits = useLive(productEditHistoryLive, [productId], { enabled: tab === 'history' })
```

Comportamento garantido (único para a aplicação inteira):
- **Montagem**: cache quente = dado instantâneo sem loading; cache frio = 1 fetch com loading.
- **`set`/`patch` em qualquer lugar** (autor da mutação, reatividade, demo) → o hook recebe o dado novo **sem nenhum fetch**.
- **`invalidate`** → re-busca silenciosa; a tela nunca "pisca".
- **Erro de fetch** → mantém o último dado; recursos independentes não se derrubam (ex.: aprovações live-only falham em demo e as edições continuam aparecendo).
- N consumidores da mesma instância = **1 fetch** (dedup em voo).

## A notificação: um único sinal

A camada emite **um único evento tipado** — `live:changed { key | prefix }` — consumido pelo `useLive`. Módulos **não declaram mais um evento de EventBus por recurso** para plumbing de dados. O EventBus continua sendo o canal para **semântica de domínio** cross-módulo (`ws:*`, `scheduling:materials:consumed`, `ui:*`...): a reatividade traduz o sinal de domínio em operações sobre recursos (`invalidate`/`set`), e o motor faz o resto.

```
[mutação local]                          [outro client]
service → API → resposta                 WS ws:{domain}:changed
   │                                        │
   ▼                                        ▼
recurso.set(resposta)   ◄─ mesmo motor ─►  reactivity → recurso.invalidate()
   │                                        │            (ou .set, se o broadcast
   ▼                                        ▼             carregar a entidade)
live:changed { key }  →  useLive  →  UI atualiza (patch = 0 fetch; invalidate = fetch silencioso)
```

## Regras

1. **Recursos vivos são declarados no service-facade do módulo** e exportados de lá — hooks importam do service (cadeia de responsabilidades intacta, §0).
2. O `fetch` do recurso passa pelo `getStrategy()` do módulo — demo/real continua decidido num ponto único (§11).
3. As chaves seguem a convenção do §10.1; o recurso é o dono da sua chave (ninguém mais toca o `cacheService` para aquele dado).
4. **Preferir `set`/`patch` a `invalidate`** sempre que o dado estiver disponível (doutrina §0.2 — tirar carga da API). `invalidate` é para dado que nasce no servidor ou sinal sem entidade.
5. Novos fluxos de dado reativo **usam a camada LIVE por padrão**. Escrever cache-first/listener à mão num hook novo é regressão de arquitetura.
6. **Gate de fetch por permissão nasce no motor** — `requires`/`requiresModule` no recurso/coleção, nunca `enabled: usePermission(...)` religado à mão no hook. Ver *Gate de fetch por permissão* abaixo.
7. **Dado recortado por permissão declara `permissionScoped`** — quem invalida em `ws:permissions:changed` é o MOTOR, nunca um listener no `xReactivity` do módulo.
8. **O motor de um módulo entra no boot; a tela é que chega sob demanda.** O `main.tsx` registra as `*Reactivity` de todos os módulos, e cada uma importa o service-facade, que declara os recursos vivos. **Módulo novo com dado próprio precisa da sua `*Reactivity` registrada lá** — ver a regra abaixo.

### Por que o registro no boot é obrigatório (e não só recomendado)

Desde o code-splitting (13-08-2026) as páginas são chunks sob demanda. O que mantém a sincronização em tempo real funcionando com a página **desmontada ou ainda não baixada** é justamente o registro no boot: 55 dos 60 recursos vivos entram no bundle inicial sem passar por página nenhuma.

Um módulo cujo motor só chega junto com a tela perde duas coisas até alguém abrir a página:

- o **resync de reconexão** (todo `defineLiveResource` se auto-registra no `liveResync` **no import**, não no uso);
- os **listeners cross-module** — o motivo original das `*Reactivity` serem nível-serviço: mudança feita por outro módulo com o dono desmontado seria perdida.

O único módulo hoje fora disso é o Billing, que está em obra e cujas mutações o server marca `broadcast: null`. Não é exceção à doutrina — é pendência registrada em `STATUS-GERAL.md` §2. **Decisão do dono: todas as páginas precisam ser reativas.**

## Coleções vivas: `defineLiveCollection`

A generalização do motor para **listas paginadas** (Etapa 2). O que era triplicado nos appliers de Procedures/Stock/Registers — upsert/remoção cirúrgicos por página, ajuste de `total`/`totalPages`, match de filtros, inserção na página 1 — vira UMA declaração no service-facade:

```ts
export const proceduresListLive = defineLiveCollection<Procedure, GetProceduresParams>({
  prefix: PROC_LIST_PREFIX,
  key: params => getProceduresListCacheKey(params),  // mesma função do cache
  ttl: CACHE_TTL.DEFAULT,
  pageSize: PROCEDURES_PAGE_SIZE,
  getId: p => p.id,
  pageOf: params => params.page ?? 1,
  isNeutral: params => !params.search && !params.category, // universo base
  matches: (p, params) => /* item pertence ao universo filtrado? */,
  sort: (items, params) => /* ordenação do módulo (opcional) */,
  fetch: async params => { /* via getStrategy() */ },
})
```

| Operação | Efeito |
|---|---|
| `getPage(params, {force?})` | Cache-first com dedup; pool completo = página **derivada localmente** (materializada na chave exata) |
| `readPage(params)` | Leitura SÍNCRONA (cache exato ou derivada do pool), zero fetch |
| `applyUpsert(next, previous, {isCreate?})` | Upsert cirúrgico em TODAS as páginas + pool: in-place preservando referências (render cirúrgico), transição entre universos de filtro (`previous`), totais e página 1. Idempotente (eco WS) |
| `applyRemove(id)` | Remoção cirúrgica + ajuste de totais |
| `seedPage(params, page)` | Semeia a 1ª página de um universo novo (ex.: categoria recém-criada) |
| `baseTotal()` / `isComplete()` | Total do universo base / dataset completo em memória |
| `invalidateAll()` | Derruba páginas + pool; consumidores re-buscam em silêncio |

O hook é o `useLiveCollection(collection, params)` → `{ page, loading, error, baseTotal, reload }` — mesmo contrato de silêncio do `useLive`; `error` sai CRU para o módulo mapear (ex.: `PageAuthorizationBlock`).

### Busca local embutida (C7 — "a aplicação precisa ser mais inteligente")

As páginas do **universo base** alimentam um *pool* acumulativo (persistido no `cacheService`, sobrevive a desmontagens). Quando o pool está completo — todos os itens do universo em memória (ex.: módulo com 1 página; ou todas as páginas navegadas) — **qualquer consulta (busca/filtro/página) é derivada localmente, instantânea, com ZERO request**. Incompleto, a consulta filtrada segue o fluxo servidor cache-first.

Dois modelos de universo:
- **Padrão** (Procedures): páginas neutras (sem filtros) carregam o total do universo no próprio `total`.
- **Universo fatiado** (Stock, category-first): as páginas do servidor são fatias por categoria — declare `poolable` (quais fatias alimentam o pool) + `universeTotal` (fonte externa do total, ex.: soma dos sumários de categoria).

O motor nunca parseia chaves de cache: os params de cada página ficam registrados no fetch. Página órfã (registro perdido, ex.: HMR) é invalidada na mutação seguinte — nunca fica stale.

## Gate de fetch por permissão: `requires` / `requiresModule`

Um recurso ou coleção pode declarar `requires: '<código do catálogo>'` — o gate FINO da convenção **"esconder o que não pode"** (nível do motor). Com ele, `useLive`/`useLiveCollection` ficam **DORMENTES** para quem não tem a capacidade (`user.capabilities` do `/me`): **zero fetch** — mata o 403 de um recurso que o servidor já sabe negado (ex.: histórico do mural, cujo modal monta sempre no dashboard). Ao **PERDER** a permissão em runtime (o `/me` re-hidrata via `ws:permissions:changed`), o hook faz **evict** do cache (recurso: `invalidate()` da instância; coleção: `invalidateAll()`) — re-conceder busca frio limpo. Sem `requires`, o comportamento é o de sempre (sempre habilitado).

```ts
export const announcementHistoryLive = defineLiveResource<AnnouncementHistoryEntry[], []>({
  key: () => HISTORY_KEY,
  ttl: CACHE_TTL.DEFAULT,
  requires: UI_GATE.ANNOUNCEMENTS_HISTORY_READ,   // ← gate de fetch = 1 palavra
  fetch: async () => { /* via getStrategy() */ },
})
```

- **Fetch gateado = 1 palavra.** Religar `enabled: usePermission(...)` à mão em cada hook é regressão (o gate nasce no motor — Regra 6).
- `requires` gateia o **fetch**. Esconder a **UI** (aba/botão/menu) é ortogonal e continua no componente com `usePermission`/`<PermissionGate>` — ex.: o hook do mural mantém `canRead` só para esconder a ABA "Histórico".
- **Não é segurança:** o servidor segue autoritativo por request. `requires` é UX — evita o fetch morto e o 403 no console.
- `usePermission(code?)` aceita código opcional (`undefined → true`), então o motor chama `usePermission(resource.requires)` incondicionalmente (regras dos hooks) sem caso especial.

### O outro nível: `requiresModule`

`requires` é o gate FINO (capacidade do `UI_GATE`, projetada em `user.capabilities`). Quando o que decide é o acesso ao MÓDULO (`moduleAccess` do `/me` — as permissões de apresentação `page`), a declaração é `requiresModule: MODULE_KEYS.<módulo>`, com a MESMA mecânica: dormência sem acesso, busca ao GANHAR, evict ao PERDER.

```ts
export const sidebarAgendaLive = defineLiveResource<SidebarAgenda, []>({
  key: () => DASHBOARD_SIDEBAR_AGENDA_CACHE_KEY,
  ttl: CACHE_TTL.DEFAULT,
  requiresModule: MODULE_KEYS.scheduling,   // ← projeção de OUTRO módulo
  permissionScoped: true,                   // ← e recortada por ownOnly
  fetch: async () => { /* via getStrategy() */ },
})
```

É o caso das PROJEÇÕES: as três sessões da sidebar do Dashboard são agenda/estoque/mensagens vistas de fora, e o servidor devolve a sessão VAZIA para quem não lê o módulo fonte. O par com `useModuleAccess(moduleKey)` (o mesmo sinal reativo) esconde o CARD — dado e UI mudam no mesmo instante.

## Conteúdo recortado por permissão: `permissionScoped`

`requires`/`requiresModule` resolvem "pode ou não pode". Existe um terceiro caso, que passava despercebido: o servidor **entrega o mesmo endpoint com outro RECORTE** — `scheduling:appointment:ownOnly` restringe a agenda aos procedimentos do profissional, a falta de `viewFinancials` REDIGE os valores. Aí o gate **não muda de valor**, nada dispara, e o dado do cargo anterior fica na tela até um F5 (o defeito relatado pelo dono em 31-07: "ganhei/perdi a permissão e a tela só atualiza recarregando").

A declaração é uma palavra:

```ts
export const monthEventsLive = defineLiveResource<RawSchedulingEvent[], [year: number, month: number]>({
  key: (year, month) => getSchedulingMonthCacheKey(year, month),
  prefix: SCHEDULING_RAW_CACHE_PREFIX,
  ttl: CACHE_TTL.DEFAULT,
  permissionScoped: true,   // ← o CONTEÚDO depende das minhas permissões
  fetch: async (year, month) => { /* ... */ },
})
```

O motor registra esses recursos no `liveResync` e, em `ws:permissions:changed`, derruba TODAS as instâncias deles — os montados re-buscam em SILÊNCIO, já com o recorte novo. **Escrever um listener de `ws:permissions:changed` no `xReactivity` do módulo para invalidar cache é regressão** — foi assim que Scheduling e Dashboard divergiram; hoje os dois declaram a flag.

Régua rápida:

| Situação | Declaração |
|---|---|
| Capacidade fina libera/nega o recurso | `requires: UI_GATE.X` |
| Acesso ao MÓDULO libera/nega o recurso | `requiresModule: MODULE_KEYS.x` |
| O recurso existe para todos, mas o CONTEÚDO muda por permissão | `permissionScoped: true` |

As três se combinam livremente (a sessão `agenda` da sidebar usa duas).

## Migrados

- **Recursos**: 8 canais de histórico (Cargos, Procedimentos, Estoque módulo+produto, Mural, Agenda, Cadastros, Franquias) + público-alvo do aviso (cargos/funcionários).
- **Sessões da sidebar do Dashboard (2026-07-31)**: `sidebarAgendaLive`/`sidebarStockLive`/`sidebarMessagesLive` — as três projeções que ainda tinham cache manual por sessão (com 3 eventos de EventBus e carga própria no hook de ações). Migradas com `requiresModule` + `permissionScoped`; morreram os eventos `dashboard:sidebar:*:updated`.
- **Recursos (C5 — as LISTAS dos módulos restantes, 2026-07-11)**: Cargos (`rolesListLive`/`roleEmployeesLive`/`permissionCatalogLive`), Franquias (`networkUnitsLive`), Mural (`announcementsLive`; a sidebar da dashboard NÃO migrou — segue granular por sessão) e Agenda (`monthEventsLive`, **família** por `[year, month]`: o calendário assina 3 instâncias — mês atual + vizinhos, o que dá o prefetch de graça; a visão diária preserva o reconcile por id). Com o C5 morreram os eventos de plumbing `roles:list/employees:updated`, `franchises:units:updated` e `dashboard:announcements:updated`; `scheduling:month:updated` permaneceu SÓ como semântica de DOMÍNIO cross-módulo (sidebar da dashboard), mesmo precedente de `registers:*:updated`.
- **Coleções**: lista de Procedimentos (piloto), páginas de produtos do Estoque (universo fatiado), clientes+funcionários de Cadastros (desativação via `applyPatch`; filtro por cargo resolvido LOCALMENTE via mapa id→nome dos roleOptions — `'unknown'` só sem o mapa em cache) e lista de Casos/Aprovações (review/cancel patcham a resposta — o caso troca de bucket de status via `previous`; cross-client re-busca SÓ o caso afetado).
- **Fora (por design)**: Mensagens — os caches são compartilhados com o hub WS do `AppLayout` (patch direto), o módulo tem socket próprio e a escrita de cache é no-op em demo; migração é frente própria.
- **Nota (`poolItems()`)**: expõe os itens do pool para derivados do módulo (ex.: stats de ativos de Cadastros) — somente-leitura, pode ser parcial (`isComplete()`).
- **Padrão do C5 p/ recurso de página**: o controller consome via `useLive`, deriva `loading = data === null && error == null`, mapeia `error` → `PageAuthorizationBlock` (403) num efeito e usa `reload()` no retry do bloqueio; mutações no service usam patch-ou-invalidate (patch com cache frio → `invalidate()` — NUNCA fabricar lista truncada a partir do vazio).
