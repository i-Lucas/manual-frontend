# 10.1 Feature Global — Cache Client

**Esta é a feature mais crítica de qualquer aplicação construída com este guia.** Implementada uma única vez, consumida diretamente por todos os módulos via `cacheService` — sem nenhuma implementação de cache por módulo. **Módulos não criam `*Cache.service.ts` próprios.**

## Por que existe — e por que é global

Em um projeto anterior, o cache foi implementado por módulo: cada módulo gerenciava seu próprio cache de forma diferente, com lógica duplicada em vários serviços espalhados por vários diretórios. O resultado: manutenção impossível, qualquer mudança de estratégia exigia refatorar múltiplos arquivos, inconsistências entre módulos eram frequentes, e módulos não conseguiam reagir a mudanças uns dos outros porque cada um enxergava apenas seu próprio cache. O custo de centralizar depois foi alto demais.

A solução definitiva é ter **uma única implementação de cache**, global, performática (`Map`), granular e com controle fino de cada recurso. Todos os módulos importam o mesmo `cacheService` — a única fonte de verdade de dados em memória da aplicação. Nenhum módulo implementa nada localmente.

**O que isso viabiliza:** conforme o usuário navega pela aplicação, todos os dados carregados são acumulados no mesmo store. Quando um módulo atualiza um recurso, ele patcha o cache e emite um evento no `EventBus`. Qualquer outro módulo que esteja ouvindo aquele evento reage imediatamente — sem nenhum acoplamento direto entre eles, e sem precisar refazer nenhum fetch.

## O que deve ser cacheado

**Tudo que vem da API. Sem exceções.** Isso inclui:

- Listas paginadas — cada página é uma chave diferente no cache
- Resultados de busca — cada termo buscado é uma chave diferente
- Resultados de filtros aplicados — cada combinação de filtros é uma chave diferente
- Detalhes de recursos individuais (produto X, pedido Y, usuário Z)
- Dados de resumo/header de módulos
- Histórico, movimentações, relatórios — qualquer dado carregado da API

Navegar entre páginas da aplicação, mudar filtros, acessar o detalhe de um produto por exemplo, voltar para a lista — tudo isso deve ser **instantâneo** porque o dado já está em cache. O carregamento com spinner deve ser a exceção, não a regra.

## O cliente sabe o que mudou

Quando o usuário realiza uma operação (atualiza o nome de um produto, cria um pedido, etc.), **não invalide o cache e não refaça o fetch**. A aplicação já sabe exatamente o que mudou — use o dado retornado pela API (`result.data`) para atualizar o cache localmente de forma cirúrgica (`patchProduct`, `patchOrder`, etc.).

```
❌ Usuário edita produto → POST /products/:id → invalidar todo o cache de produtos → re-fetch da lista
✅ Usuário edita produto → POST /products/:id → patchProduct(result.data) → UI atualiza imediatamente
```

O re-fetch só deve acontecer quando outro agente externo (outro usuário, processo do servidor, webhook) pode ter alterado o dado — e nesse caso, o TTL cuida da expiração automática.

## Granularidade por sessão e recurso

Cada sessão de uma página tem seu próprio estado de carregamento e seu próprio cache. Se o cache do header expirou, apenas o header mostra o spinner/skeleton e recarrega. O restante da página permanece intacto.

Da mesma forma, se um módulo externo atualizou um produto específico via `EventBus`, apenas aquele produto é atualizado na tabela — não a lista inteira, não o módulo inteiro. O `patchProduct` no cache garante que somente a linha daquele produto re-renderize.

```
Página: Estoque
├── InventoryHeader     → cache: inventory:header:_:summary:_     (TTL: 1min)
├── InventoryAlerts     → cache: inventory:alerts:_:active:_      (TTL: 30s)
├── InventoryFilters    → sem cache (estado local de UI)
├── InventoryTable      → cache: inventory:table:{page}:list:{filter+search}  (TTL: 2min)
│   ├── produto abc-123 → cache: inventory:product:abc-123        (TTL: 5min)
│   └── produto def-456 → cache: inventory:product:def-456        (TTL: 5min)
└── InventoryPagination → derivado do cache da tabela
```

Se `abc-123` foi atualizado externamente → apenas a linha `abc-123` re-renderiza. As outras sessões não são afetadas.

## TTL baseado na volatilidade do dado

O TTL (tempo de expiração automática) deve refletir a criticidade e frequência de atualização de cada tipo de dado. O Agente deve avaliar cada dado ao definir o TTL — não usar um valor único para tudo.

| Tipo de dado | TTL sugerido | Motivo |
|---|---|---|
| Alertas críticos | 30s | Alta prioridade, deve ser fresco |
| Resumo/header | 1min | Visível o tempo todo, não pode ficar desatualizado |
| Lista paginada | 2 – 3min | Baixa volatilidade, cara pra recarregar |
| Detalhe de recurso | 5 – 10min | Raramente muda sem ação do usuário |
| Dados de relatório / histórico | 10 – 30min | Praticamente estáticos por sessão |

## Implementação

```ts
// src/services/cache/cacheStore.ts
/**
 * @description Store de cache em memória com suporte a TTL por chave.
 * Baseado em Map para performance máxima (O(1) para get/set/delete).
 * Mantém Maps separados para dados e metadados (timestamps).
 */
import type { CacheEntry, CacheStats } from './models/cache.types';

/** Map principal de dados em cache */
const store = new Map<string, CacheEntry<unknown>>();

function isExpired(entry: CacheEntry<unknown>): boolean {
  return Date.now() > entry.expiresAt;
}

export const cacheStore = {
  get<T>(key: string): T | null {
    const entry = store.get(key);
    if (!entry) return null;
    if (isExpired(entry)) {
      store.delete(key);
      return null;
    }
    return entry.data as T;
  },

  set<T>(key: string, data: T, ttlMs: number): void {
    store.set(key, {
      data,
      expiresAt: Date.now() + ttlMs,
      createdAt: Date.now(),
    });
  },

  delete(key: string): void {
    store.delete(key);
  },

  /** Invalida todas as chaves com determinado prefixo */
  invalidateByPrefix(prefix: string): void {
    for (const key of store.keys()) {
      if (key.startsWith(prefix)) store.delete(key);
    }
  },

  /**
   * Atualiza um item específico dentro de uma lista cacheada, sem invalidar o resto.
   * T deve ser um objeto com uma propriedade identificadora (ex: 'id').
   * Usado para operações otimistas e reações a eventos do EventBus.
   */
  patch<T extends Record<string, unknown>>(key: string, updatedItem: T, idField: keyof T = 'id' as keyof T): void {
    const entry = store.get(key);
    if (!entry) return;
    const list = entry.data as T[];
    if (!Array.isArray(list)) return;
    const index = list.findIndex(item => item[idField] === updatedItem[idField]);
    if (index === -1) return;
    list[index] = { ...list[index], ...updatedItem };
  },

  /** Invalida todas as chaves expiradas (cleanup manual) */
  purgeExpired(): number {
    let count = 0;
    for (const [key, entry] of store.entries()) {
      if (isExpired(entry)) { store.delete(key); count++; }
    }
    return count;
  },

  /** Estatísticas para debug/monitoramento */
  getStats(): CacheStats {
    let expired = 0;
    for (const entry of store.values()) {
      if (isExpired(entry)) expired++;
    }
    return { total: store.size, expired, active: store.size - expired };
  },

  clear(): void {
    store.clear();
  },
};
```

```ts
// src/services/cache/cacheService.ts
/**
 * @description Facade público do serviço de cache.
 * Todos os módulos consomem apenas esta interface.
 * Agenda limpeza periódica de entradas expiradas.
 */
import { cacheStore } from './cacheStore';
import type { CacheStats } from './models/cache.types';

// Limpeza periódica de entradas expiradas (a cada 5 minutos)
setInterval(() => cacheStore.purgeExpired(), 5 * 60 * 1000);

export const cacheService = {
  get: cacheStore.get.bind(cacheStore),
  set: cacheStore.set.bind(cacheStore),
  delete: cacheStore.delete.bind(cacheStore),
  patch: cacheStore.patch.bind(cacheStore),
  invalidateByPrefix: cacheStore.invalidateByPrefix.bind(cacheStore),
  getStats: (): CacheStats => cacheStore.getStats(),
  clear: cacheStore.clear.bind(cacheStore),
};
```

## Convenção obrigatória de chaves de cache

```
{module}:{section}:{page}:{resource}:{id}

Exemplos:
inventory:list:1:products:_          ← lista de produtos, página 1
inventory:header:_:summary:_         ← resumo do header
inventory:table:1:products:abc-123   ← produto específico na tabela
orders:list:3:pending:_              ← pedidos pendentes, página 3
dashboard:summary:_:kpis:_           ← KPIs da dashboard
```

## Fluxo reativo: cache + EventBus

O cache e o EventBus trabalham juntos para manter a aplicação reativa sem re-fetches desnecessários. O padrão é sempre o mesmo:

```
[Ação do usuário]
       │
       ▼
service-api chama o repository (fetch real)
       │
       ▼
cache.patch(chave, dadoAtualizado)     ← atualização cirúrgica, sem invalidar o resto
       │
       ▼
eventBus.emit('modulo:recurso:updated', { id })   ← avisa quem estiver ouvindo
       │
       ├──▶ hook do próprio módulo reage → UI atualiza instantaneamente
       │
       └──▶ hook de outro módulo que fez subscribe → UI desse módulo também atualiza
```

**Exemplo concreto:** usuário edita o produto `abc-123` no módulo de Estoque.

```ts
// inventoryService.ts
async function updateProduct(id: string, data: Partial<Product>): Promise<Result<Product>> {
  const result = await inventoryRepository.update(id, data);
  if (!result.ok) return result;

  // Patch cirúrgico: atualiza só esse produto no cache da lista e no cache do detalhe
  cacheService.patch('inventory:table:1:products:_', result.data);
  cacheService.set(`inventory:table:_:products:${id}`, result.data, TTL.PRODUCT);

  // EventBus avisa qualquer módulo que esteja ouvindo
  eventBus.emit('inventory:product:updated', { productId: id });

  return result;
}
```

```ts
// dashboardService.ts (em outro módulo, ouvindo o evento)
eventBus.on('inventory:product:updated', ({ productId }) => {
  // Invalida apenas o resumo de estoque crítico na dashboard
  cacheService.invalidateByPrefix('dashboard:summary:_:stock');
  // O hook da dashboard vai detectar a invalidação e re-renderizar só aquela sessão
});
```

O resultado: a Dashboard atualiza a sessão de estoque crítico instantaneamente, sem que o módulo de Estoque conheça a Dashboard, e sem que nenhum fetch extra seja feito.

## Como os módulos consomem o cache

**Módulos não criam serviços de cache próprios.** O `cacheService` é importado diretamente pelo `service-facade` de cada módulo.

```ts
// ✅ correto — inventoryService.ts importa o cacheService global
import { cacheService } from '@/services/cache/cacheService';

// ❌ errado — módulo NÃO cria inventoryCache.service.ts nem nada parecido
import { inventoryCache } from './inventory-cache/inventoryCache.service';
```

A pasta `services/` de um módulo contém apenas: `repository/`, `inventoryService.ts` (facade) e sub-services específicos de domínio (validators, calculators, etc.). **Cache nunca é um sub-service de módulo.**
